# ADR: Consolidate the designer on `product_designs`, bridged by its uuid

## Status

Accepted 2026-08-04. Shipped in `abcf0a82`.

## Context

Two designer subsystems were live at once:

- **Legacy** — `designs` (uuid PK), `components/storefront/designer/`, served at
  `/sites/[domain]/designer/[slug]`.
- **Current Print Designer** — `product_designs` (integer PK), `product_styles` /
  `product_sides`, `components/product-designer/`, served at
  `/sites/[domain]/design/[slug]`.

They shared the `/api/storefront/[siteId]/designs` API, which dispatches on id shape.
But `cartItems.designId` is a `uuid` column, and the cart route validated against a
36-character uuid before joining the legacy `designs` table. The current designer's
integer ids could not satisfy that check, so **a design made in the current designer
could never reach a cart.** Customers could design; they could not buy.

Keeping both was not viable — one of them had to own the cart.

## Decision

Consolidate on `product_designs`, and bridge it into the existing uuid column using
the `uuid` share-link field it already carries.

The row counts decided which subsystem survives:

| | Legacy `designs` | Current `product_designs` |
|---|---|---|
| Customer designs | 11 (QA scratch) | **0 — nothing to migrate** |
| Print-area config | 22 surfaces | **180 styles + 695 sides** |

The expensive, hand-built asset — colorway and per-side printable bounds — sits
entirely on the current side. Legacy's only advantage was that its uuid happened to
match the cart column, and that is one column, not 875 rows of configuration. The
current per-style/per-side model is also the correct one for print-on-demand, where
print bounds differ per colorway.

## Consequences

**No schema change, and no migration.** `productDesigns.uuid` is generated by
`crypto.randomUUID()`, so it is a valid RFC 4122 value and stores cleanly in the
existing `uuid` column. The cart keeps its column; only the lookup target changed.

This avoided a `uuid → integer` type change on `cart_items` and `order_items`. That
matters beyond tidiness: type changes are **not additive**, so the "Prod schema sync
(additive)" workflow cannot apply them, and they require a hand-written guarded
`*_manual.sql` against metro. An unapplied migration of exactly that class took
production down on 2026-07-11.

The join needs an explicit cast — `productDesigns.uuid` is `varchar(36)` against a pg
`uuid` column, and without `::text` Postgres raises
`operator does not exist: character varying = uuid`. Verified against a real database,
not assumed.

Soft-deleted designs are now filtered out of the cart join, which the previous
implementation missed.

## Notes

The legacy subsystem is now dead weight but not yet deleted — tracked as PODR-005.
`products.isDesignable` and `products.designable` are **not** duplicate columns: they
select which designer a product uses (legacy vs current). `isDesignable` only becomes
droppable once the legacy path is removed.
